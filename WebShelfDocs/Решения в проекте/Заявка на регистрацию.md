# Заявка на регистрацию

## Назначение

Окно «Подача заявки на регистрацию» (страница `/entry`, компонент `Entry.razor`, форма — `RegistrationApplicationForm.razor`) — анкета кандидата, предъявившего действующий пермит. Окно открывается из окна «Активация разрешения» кнопкой «Продолжить» после успешной проверки пермита в БД и закрывается кнопкой «×» с возвратом на окно «Вход в систему».

Учётные записи в приложении создаёт администратор через Active Directory (см. [[Пользователи]]): заявка хранит контактные данные кандидата для проверки администратором (таблица `webshelf.registration_requests`, см. [[База данных]]); обмен пермита на учётную запись — отдельная задача (см. [[Активация разрешения]]).

## Поведение (реализовано)

### Окно «Активация разрешения»: кнопка «Продолжить»

1. Значение поля «Пермит» (обрезается по краям) проверяется сервисом `RegistrationPermitChecker` точным совпадением в таблице `webshelf.registration_permits` (параметризованный запрос, только чтение).
2. Пермит найден и его счётчик оставшихся регистраций **больше нуля** — открывается окно «Подача заявки на регистрацию»; введённый пермит сбрасывается.
3. Пермит не найден, пуст или счётчик равен нулю — окно активации закрывается, пользователь возвращается на окно «Вход в систему», а кнопка **«Зарегистрироваться» блокируется на 15 секунд с обратным отсчётом** в тексте кнопки («Регистрация доступна через N с.», `CountdownLockout`).
4. Ошибка сервера (БД недоступна и т.п.) не списывается на пользователя: окно активации остаётся открытым, под полем выводится сообщение об ошибке, повторная попытка возможна сразу; блокировка в этом случае не включается.
5. На время проверки поле и кнопка «Продолжить» блокируются — исключён повторный запуск проверки.

### Окно «Подача заявки на регистрацию»: форма

1. Поля: **Фамилия, Имя, Отчество** (текст), **E-Mail** (`type=email`), **Номер телефона** (`type=tel`). Все поля обязательны к заполнению (`required`).
2. Телефон вводится в формате **+7 (XXX) XXX-XX-XX**: по мере ввода цифры автоматически укладываются в маску (`RegistrationFormValidator.ApplyPhoneMask`) — ведущая 7/8 считается кодом страны, посторонние символы отбрасываются, значащих цифр не больше 10.
3. Автоматическая проверка форматов выполняется по мере ввода (`RegistrationFormValidator`): некорректный e-mail, неполный телефон, посторонние символы или превышение длины в ФИО — красная рамка поля и текст ошибки под ним. Ошибки показываются после первого касания поля (blur) и обновляются при каждом вводе; до касания форма чистая.
4. Чек-бокс **согласия на обработку персональных данных**: обязателен, в подписи — состав данных, цель, ссылка на 152-ФЗ и на [[Обработка персональных данных|политику обработки персональных данных]] (открывается в новой вкладке). Формулировка соответствует ч. 1 ст. 9 152-ФЗ и приказу Роскомнадзора № 18.
5. Кнопка **«Подать заявку»** — заглушка по задаче: поведение при нажатии отсутствует, обработка отправки появится вместе с логикой регистрации (аналогично бывшей заглушке «Продолжить»).
6. Закрытие окна «×» возвращает на окно «Вход в систему»; введённые данные заявки сбрасываются (компонент формы размонтируется вместе с окном).

## Решения

**Решение (счётчик пермита не уменьшается при проверке):** проверка только читает состояние. Счётчик уменьшается при успешной регистрации, а не при открытии формы — пермит нельзя «сжечь», закрыв окно заявки без отправки (поведение счётчика — см. [[База данных]]).

**Решение (блокировка 15 с — на кнопке, а не на всей форме):** неудачная проверка пермита блокирует только кнопку «Зарегистрироваться» (с отсчётом в тексте кнопки) — вход в систему по имеющимся учётным записям не затрагивается. Блокировка формы входа после неудачных попыток входа устроена иначе (LoginGuard) и остаётся без изменений. Логика отсчёта выделена в `CountdownLockout` (чистый класс, покрыт юнит-тестами); таймером владеет страница, тики выполняются в контуре Blazor (InvokeAsync).

**Решение (значение пермита не попадает в логи):** пермит — секретный код. В логи пишется только статус проверки (Usable/NotFound/Exhausted) и счётчик; значение пермита не логируется ни при каких условиях (правило маскировки, [[Логирование]]).

**Решение (ссылка согласия открывается в новой вкладке):** переход по ссылке политики — полная навигация (статичный документ вне Blazor-роутинга). Открытие в той же вкладке разорвало бы цепь Blazor и потеряло введённые данные заявки; `target="_blank" rel="noopener"` сохраняет форму.

**Решение (валидация в чистом классе, а не в компоненте):** все проверки форматов и тексты ошибок — в `RegistrationFormValidator` (чистые функции, покрыты тестами). Компонент только хранит значения и признаки «поле тронуто»; при появлении серверной обработки заявки тот же валидатор применяется на стороне эндпоинта.

**Решение (состояние формы сбрасывается закрытием окна):** окна страницы `/entry` показываются по очереди; при закрытии окна заявки компонент формы размонтируется — введённые данные не переживают закрытие. Повторное открытие (новая проверка пермита) начинает с чистой формы.

## Ограничения текущей реализации

- Кнопка «Подать заявку» не выполняет действий: заявка не записывается в `webshelf.registration_requests` (обработка отправки — вместе с логикой регистрации).
- Проверка пермита не защищена серверной эскалацией: каждая неудачная попытка даёт фиксированные 15 с блокировки кнопки (без удвоения, как у LoginGuard).
- Блокировка «Зарегистрироваться» живёт в состоянии страницы: обновление страницы (/entry) снимает её досрочно.
