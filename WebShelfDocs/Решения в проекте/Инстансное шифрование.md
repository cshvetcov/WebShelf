# Инстансное шифрование

## Что защищается

Пароли и логины сервисных учётных записей хранятся в `Server.conf` **только в зашифрованном виде**:

| Ключ конфигурации | Назначение |
| ----------------- | ---------- |
| `sdomainuser` / `sdomainpass` | Сервисная учётная запись Active Directory |
| `sdbuser` / `sdbpass` | Сервисная учётная запись PostgreSQL |
| `scertpass` | Пароль PFX-сертификата (TLS) |

Открытые пары (`domainuser`/`domainpass`, `dbuser`/`dbpass`, `certpass`) при первом
запуске автоматически шифруются и переносятся в защищённые ключи, открытые
значения затираются (атомарная замена файла — временный файл + `File.Replace`).

Мастер-ключ шифрования создаётся `KeyStore`: хранится в реестре
`HKCU\Software\WebShelf\Encryption` под защитой DPAPI текущей учётной записи
Windows, привязан к InstanceId (ULID) инстанса, в памяти — sliding-TTL кэш
(см. [[Пользователи]]).

## Криптоформат (заморожен)

`CryptoEngine` выполняет аутентифицированное шифрование **AES-256-GCM (AEAD)**.
Формат полезной нагрузки:

```
[1 байт версия = 2] | [12 байт nonce] | [N байт ciphertext] | [16 байт тег GCM]
```

- **Вывод ключа**: ключ AES-256 выводится из мастер-ключа через
  **HKDF-SHA256** (RFC 5869) по фиксированной метке
  `WebShelf.Classes.Crypto.CryptoEngine.AES-GCM.v2`; соль — 32 нулевых байта
  (значение по умолчанию RFC 5869, зафиксировано явно). Метка и соль — часть
  замороженного формата.
- **Nonce**: случайные 96 бит (`RandomNumberGenerator`). Ограничение NIST SP
  800-38D на случайные nonce — не более 2^32 шифрований на ключ; для объёмов
  `Server.conf` (единичные записи) запас избыточен, формат не предназначен
  для крупных массивов данных.
- **Целостность**: тег GCM покрывает nonce, шифртекст и AAD — аутентификация
  выполняется самим режимом шифрования, критическая операция проверки
  реализована внутри BCL. Ключевой материал обнуляется в `finally`.
- **Заморозка**: формат зафиксирован эталонной константой совместимости в
  `CryptoEngineTests` (фиксированный вектор: ключ `0x00..0x1F`, nonce
  `0x00..0x0B`, фиксированные открытый текст и контекст). Изменение любого
  элемента схемы (версия, метка/соль вывода ключа, порядок полей, состав AAD,
  алгоритмы) делает конфиги инсталляций нечитаемыми — это защита от случайных
  правок, а не баг.

## Привязка к контексту (AAD)

Каждый вызов `Encrypt`/`Decrypt` передаёт обязательный **контекст шифрования** —
метку назначения данных. Контекст подмешивается в AAD вместе с версией
формата (`AAD = версия ‖ контекст`), поэтому блоб привязан к назначению:
расшифровка в чужом контексте завершается сбоем проверки тега. На практике
это закрывает перестановку зашифрованных значений между полями `Server.conf`
(splicing): блоб `sdbpass`, подложенный в `sdomainuser`, не пройдёт проверку
целостности, хотя сам по себе не изменён.

Канонические значения контекстов собраны в `CryptoContexts` и являются частью
замороженного формата:

- для полей `Server.conf` контекст совпадает с именем ключа конфигурации
  (`sdomainuser`, `sdomainpass`, `sdbuser`, `sdbpass`, `scertpass`);
- для внутренних полей классов используется полное имя класса-владельца
  (`Domain` перешифровывает нормализованный логин и пароль в собственные поля
  с контекстами `WebShelf.Classes.DC.Domain.ServiceUser` / `...ServicePassword`).

## Архитектура: DI-сервисы

Криптографические сервисы — инстансные singleton'ы:

- `KeyStore` и `CryptoEngine` создаются в `Program.Main` **до** сборки хоста
  (Data и инициализаторы секций читают `Server.conf` и расшифровывают учётные
  данные, когда DI-контейнер ещё не существует), после чего регистрируются в
  DI как готовые экземпляры (`AddSingleton(instance)`);
- `Data` получает оба сервиса конструктором и передаёт их инициализаторам
  секций (`DomainSection`, `DatabaseSection`, `CertificateSection`);
- `Domain` и `Database` получают криптографию конструктором: `KeyStore` —
  источник мастер-ключа, `CryptoEngine` — шифрование/расшифровка учётных
  записей (расшифровка и валидация выполняются однократно в конструкторе);
- методы криптосервисов объявлены `virtual` — единственная гибкость поверхности,
  необходимая для подмены фейком в юнит-тестах; движок не содержит состояния.

**Причина — тестируемость.** Подмена хранилища ключей фейком
(`CryptoTestFakes.FakeKeyStore` с синтетическим ключом) позволяет выполнять
сценарии, требующие мастер-ключа, на любой ОС — без реестра HKCU и DPAPI.
Реальные сценарии хранилища (запись/чтение реестра, DPAPI) остаются покрытыми
в `KeyStoreTests` с обязательным Windows-прогоном.

**Следствия для сопровождения:**

- при добавлении нового потребителя криптографии зависимость внедряется через
  конструктор (инстанс `KeyStore`/`CryptoEngine` из DI), статических обращений
  быть не должно;
- новому назначению зашифрованных данных соответствует новый контекст:
  константа добавляется в `CryptoContexts`; переиспользовать чужой контекст
  нельзя (блоб станет взаимозаменяемым между назначениями), менять значение
  существующей константы — тем более (это смена формата);
- регистрации криптосервисов зафиксированы тестом `CryptoRegistrationTests`:
  при изменении состава регистраций в `Program.cs` обновите список там;
- форматы и алгоритмы движка менять запрещено (см. «Криптоформат»); эталонный
  тест — механизм принудительной остановки такой правки.
