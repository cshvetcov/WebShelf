# Инстансное шифрование

## Переход со статического фасада на DI-сервисы

**Реализовано (шаг 8 декомпозиции, улучшение У3).** Криптографические сервисы — хранилище ключей `KeyStore` и движок шифрования `CryptoEngine` (см. [[Пользователи]]) — переведены со статического класса `EncryptionService` на инстансную модель с внедрением зависимостей:

- `KeyStore` и `CryptoEngine` — обычные классы; экземпляры создаются в `Program.Main` **до** сборки хоста (Data и инициализаторы секций читают `Server.conf` и расшифровывают учётные данные, когда DI-контейнер ещё не существует), после чего регистрируются в DI как готовые singleton-экземпляры (`AddSingleton(instance)`);
- `Data` получает оба сервиса конструктором и передаёт их инициализаторам секций (`DomainSection`, `DatabaseSection`, `CertificateSection`);
- `Domain` и `Database` получают криптографию конструктором (`KeyStore` — источник мастер-ключа, `CryptoEngine` — шифрование/расшифровка учётных записей); сигнатуры их конструкторов изменены, точки создания (секции, тесты) переведены;
- статический класс `EncryptionService` удалён; вызовы шифрования и расшифровки выполняются только через инстансные зависимости.

**Причина — тестируемость.** Статический фасад не позволял подменять криптографию в тестах: сценарии, которым нужен мастер-ключ (полный конструктор `Domain`/`Database`, миграция учётных данных при чтении `Server.conf`), требовали реального ключа из реестра HKCU под защитой DPAPI и выполнялись только на Windows. Теперь хранилище ключей подменяется фейком (`CryptoTestFakes.FakeKeyStore` с синтетическим ключом), и эти сценарии тестируются на любой ОС; реальные сценарии хранилища (запись/чтение реестра, DPAPI) остаются покрытыми в `KeyStoreTests` с обязательным Windows-прогоном.

**Поведения не менялось.** Криптоформат «версия | IV | ciphertext | MAC» и метки вывода ключей заморожены эталонной константой совместимости; реестровые ключи, `Server.conf`, логи — без изменений. Кэш мастер-ключа и блокировки перенесены со статического уровня на уровень экземпляра `KeyStore` — в Production экземпляр один (singleton), семантика прежняя. Методы криптосервисов объявлены `virtual` — единственное изменение поверхности, необходимое для подмены фейком; изменение форматов или алгоритмов шагом не выполнялось.

**Следствия для сопровождения:**

- при добавлении нового потребителя криптографии зависимость внедряется через конструктор (инстанс `KeyStore`/`CryptoEngine` из DI), статических обращений быть не должно;
- тестам, которым нужен произвольный валидный ключ, следует использовать `CryptoTestFakes.FakeKeyStore` + реальный `CryptoEngine`; сценарии реального DPAPI-хранения — в `KeyStoreTests` (Windows);
- регистрации криптосервисов зафиксированы тестом `CryptoRegistrationTests` (по образцу `RoleModelRegistrationTests`): при изменении состава регистраций в `Program.cs` обновите список там.
