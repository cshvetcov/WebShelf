# Версионирование политик

## Назначение

Документ фиксирует устройство журнала версий (редакций) политик обработки файлов cookie и обработки персональных данных: откуда берётся текст политики, как создаётся и нумеруется новая редакция, где хранятся предыдущие редакции, откуда страница берёт номер версии, дату изменения и контрольную сумму, и как согласие на обработку cookie связано с редакцией политики. Документ рассчитан на оператора персональных данных (организацию, разворачивающую WebShelf) и на разработчиков.

## Принятые решения (сводка)

1) **Оформление — Razor-шаблон, контент — динамически.** Оболочка страниц политик (окно, заголовок, стили) рендерится компонентом `PolicyDocument.razor`; текст редакции подгружается при рендере страницы из журнала в БД. Дублирование ~150 строк стилей в двух статичных HTML-файлах и проблема предсжатых копий `.gz`/`.br` устранены.

2) **Авторский источник текста — поставка, рантайм-источник — журнал БД.** Тексты правятся в репозитории (`WebShelf/Content/Policies/*.html`, копируются в вывод сборки): юридический текст проходит ревью вместе с кодом. При старте `PolicyContentService` синхронизирует поставку с журналом `webshelf.policy_versions` — та же философия, что у каркаса БД: файл поставки → приложение приводит хранилище к нему при старте.

3) **Журнал — append-only.** Строки журнала никогда не обновляются и не удаляются: новая редакция вставляется только при изменении контрольной суммы текста. Возврат текста, совпадающего с любой из ранее опубликованных редакций, новой строки не создаёт — защита от случайного отката публикации более старой поставкой (например, перезаписью каталога приложения предыдущей сборкой).

4) **Версия — целое число в пределах политики.** Нумерация с 1, монотонно растёт; актуальная редакция — `MAX(version)`. Флагов `is_current` нет — их невозможно рассинхронизировать.

5) **Дата вступления редакции — момент вставки** (UTC, `effective_from`). Это дата, когда текст реально начал показываться пользователям: юридически корректная «дата редакции» вместо вписываемой вручную даты.

6) **Контрольная сумма — SHA-256** канонизированного текста (UTF-8, LF, без BOM): стабильно между git (LF/CRLF), Windows-развёртыванием и БД. Хранится в строке журнала, выводится в блоке «История редакций» и на архивной странице — доказательная «отпечатка» редакции.

7) **Реквизиты оператора — неотъемлемая часть текста политики.** Поля «ЗАПОЛНИТЬ ПРИ РАЗВЁРТЫВАНИИ» остаются в тексте и версионируются вместе с ним: заполнение реквизитов оператором — это публикация следующей редакции (правка файла в каталоге приложения + перезапуск). Решение оператора: параметры не подгружаются из конфигурации.

8) **Согласие на cookie привязано к редакции политики.** Запись решения в localStorage хранит номер редакции; после публикации новой редакции сохранённое решение считается отсутствующим, и баннер запрашивает согласие заново (информированность согласия, ст. 9 152-ФЗ).

9) **Согласия формы заявки фиксируются с номерами редакций.** При подаче заявки на регистрацию в таблицу `webshelf.registration_requests` записываются номера действующих редакций обеих политик (`personal_data_policy_version`, `cookie_policy_version`) и время подачи по UTC — какое согласие и на какую редакцию дано, доказуемо записью в БД (см. [[Заявка на регистрацию]]).

## Архитектура

```
Репозиторий (разработка)                     Экземпляр (развёртывание)
Content/Policies/cookie-policy.html     ───► при старте PolicyContentService.SyncFromDeliveryAsync:
Content/Policies/personal-data-…html          SHA-256(файла) ≠ SHA-256(последней строки)?
                                               ├─ да, и суммы нет в журнале → INSERT редакции №N+1
                                               ├─ да, но сумма уже есть (откат)  → пропуск (Warning)
                                               └─ нет → ничего
                                                     │
Запросы (SSR, без интерактивности):                 ▼
/cookie-policy.html, /personal-data-policy.html → журнал webshelf.policy_versions
/policy/{code}/{version} (архив)            → (кэш актуальных редакций после старта)
```

- Синхронизация выполняется в `Program.Main` после `DbBootstrapper.EnsureSchemaAsync` — синхронно с точкой старта (`await`). Ошибка (файл не найден, вставка не выполнена, пустой журнал) останавливает приложение (fail-fast): без текста политики информирование субъектов невозможно.
- Вставка атомарна: номер `MAX(version)+1` и защита от дубля суммы в одном операторе `INSERT … SELECT … WHERE NOT EXISTS`; `UNIQUE(policy, version)` — страховка от гонки параллельных стартов.
- Подгрузка контента — **серверная, при рендере SSR-страницы**, а не fetch с клиента: не нужен JS, нет вопросов к CSP, нет «мигания» пустой оболочки.

## Схема данных

Таблица `webshelf.policy_versions` (каркас БД, версия 4):

| Столбец | Тип | Назначение |
| --- | --- | --- |
| `id` | bigint | суррогатный первичный ключ (sequence) |
| `policy` | text | код политики: `cookie` / `personal-data` (CHECK-домен) |
| `version` | integer | номер редакции в пределах политики, с 1; `UNIQUE(policy, version)` |
| `effective_from` | timestamptz | дата и время вступления редакции в силу (UTC) |
| `content` | text | канонизированный HTML-текст редакции (фрагмент без оболочки и h1) |
| `content_sha256` | varchar(64) | контрольная сумма SHA-256 текста (hex) |
| `created_at` | timestamptz | техническое время вставки |

Индекс `policy_versions_policy_idx (policy)` — выборки актуальной редакции и истории. Таблица автономна (без FK), как и остальные таблицы схемы.

**ВАЖНО (для следующих правок каркаса):** CHECK-домен записан в форме вывода `pg_get_constraintdef` — `CHECK (((policy = 'cookie'::text) OR (policy = 'personal-data'::text)))`: PostgreSQL депарсит сравнение литералов со столбцом `text` с приведением `::text`, и каркас обязан записывать литералы в этом же виде, иначе контрольная проверка после применения каркаса не сойдётся (см. комментарий в `db/webshelf_skeleton.sql`).

Каталог политик — `PolicyCatalog`: соответствие «код — файл — заголовки» для обеих политик; страницы, сервис и тесты опираются только на него. Коды фиксированы CHECK-ограничением: новая политика требует синхронного расширения каркаса и каталога.

## Страницы

| Адрес | Что показывает |
| --- | --- |
| `/cookie-policy.html` | Актуальная редакция cookie-политики |
| `/personal-data-policy.html` | Актуальная редакция политики обработки ПД |
| `/policy/{code}/{version}` | Архивная редакция с плашкой: период действия, контрольная сумма, номер актуальной редакции |

- **Адреса актуальных страниц сохранены** со времён статичных страниц: ссылки футера, баннера согласия, чек-бокса согласия формы заявки, взаимные ссылки текстов и закладки пользователей не меняются.
- Страницы — статический SSR без интерактивности; layout `PolicyLayout` (без ленты, футера и баннера) подключает `css/policy.css` и `noindex`. Скриптов нет (CSP `script-src 'self'`).
- На странице: `h1` и строка «Редакция №N от ДД.ММ.ГГГГ» (из метаданных строки журнала, локальное время сервера), текст редакции, кнопка «Вернуться в систему» и блок «История редакций» (№, дата, контрольная сумма, ссылки на архивные редакции; выводится при более одной редакции).
- Блок истории даёт пользователям доступ к предыдущим редакциям — требование прозрачности изменения политики.
- Запрошенная на архивной странице актуальная редакция показывается без плашки (эквивалент основной странице); несуществующий код или номер — резервное сообщение.

## Целостность

- При чтении редакции контрольная сумма **пересчитывается** из хранимого текста и сравнивается со строкой журнала: несовпадение — текст изменён вне журнала — `PolicyContentIntegrityException`, рендер прерывается (fail-fast) и попадает в обработчик ошибок приложения.
- Актуальные редакции и история кэшируются в памяти после синхронизации (редакции меняются только при старте): отображение страницы не обращается к БД. Правки журнала напрямую в БД видны после перезапуска.
- Канонизация идемпотентна (BOM, CRLF→LF): сумма хранимой строки пересчитывается тем же путём, что при вставке.

## Согласие на cookie и редакции политики

Запись решения в localStorage (`ws-cookie-consent`) дополнена полем `policyVersion` — номером редакции cookie-политики, на момент которой дано согласие:

- `hasDecision(policyVersion)` возвращает `false`, если сохранённое решение относится к другой редакции — баннер переспрашивает согласие после публикации новой редакции;
- `CONSENT_VERSION` в `CookieConsent.razor.js` остаётся **версией формата записи** (растёт только при изменении состава полей), ручное сопровождение номера редакции не требуется;
- записи старого формата (без `policyVersion`) решением не считаются — баннер переспросит один раз; баннер по умолчанию выключен, на практике влияния нет;
- чек-лист включения согласия в [[Обработка cookie]] упрощён: публикация новой редакции политики автоматически перезапрашивает согласие.

## Развёртывание и обновление

**Новый экземпляр:** пустая схема → каркас v4 → первая синхронизация вставляет редакции №1 (дата — момент первого старта).

**Обновление развёрнутого экземпляра** (в поставке появилась таблица журнала):

1) удалить из `wwwroot` опубликованной копии прежние статичные страницы `cookie-policy.html`, `personal-data-policy.html` и их предсжатые копии `.gz`/`.br` — иначе статические файлы будут перекрывать маршруты Razor тех же адресов;
2) на один запуск включить `dbautoschemareset=true` в Server.conf: каркас приведёт схему Structure Update'ом (таблица добавится; перед изменением непустой схемы автоматически создаётся дамп), затем вернуть `false`;
3) перезапустить приложение — будут вставлены редакции №1 с текстом поставки;
4) заполнить реквизиты оператора в `Content/Policies/*.html` и перезапустить — реквизиты зафиксируются редакцией №2.

**Изменение текста политики** — правка фрагмента в репозитории (или в каталоге приложения на месте) и перезапуск: новая редакция фиксируется автоматически, откат — нет.

## Ограничения

- Обновление текста требует перезапуска приложения (журнал пополняется только при старте). «Горячая» публикация без рестарта — будущая страница администратора; точка подключения — методы `PolicyContentService`.
- Редакция №1 обновляемого экземпляра получает дату первого старта с журналом; исторических редакций до внедрения журнала не существует.
- Строки журнала не удаляются (юридическая история); чистка возможна только вместе со сбросом схемы БД.
- `css/policy.css` подключается обычным относительным href (не карта ресурсов `Assets`): компоненты страниц рендерятся и вне интерактивного контура; кэш-бастинг для стилей не используется.
