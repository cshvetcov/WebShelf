# База данных

## СУБД и драйвер

- СУБД — **PostgreSQL**. Драйвер — **Npgsql** (пакет `Npgsql`), для работы с результатами запросов подключён **Dapper** (пакет `Dapper`).
- Все классы, связанные с управлением базой данных, размещаются в пространстве имён `WebShelf.Classes.DB` (см. [[Пространства имен]]).
- Центральный класс — `WebShelf.Classes.DB.Database`: хранит параметры соединения и единый `NpgsqlDataSource` на весь срок жизни процесса. Экземпляр создаётся один раз при старте приложения и доступен через `Data.Database`. Класс неизменяем после создания и потокобезопасен.

## Конфигурация подключения (Server.conf)

| Ключ | Назначение |
| --- | --- |
| `dbhost` | Хост PostgreSQL (имя или IP). Обязательный. |
| `dbport` | Порт PostgreSQL (1–65535). По умолчанию 5432. |
| `dbname` | Имя базы данных. Обязательный. |
| `dbsslmode` | Режим SSL/TLS: `Disable`, `Allow`, `Prefer`, `Require`, `VerifyCA`, `VerifyFull`. По умолчанию `Require`. |
| `dbuser` / `dbpass` | Открытые учётные данные сервисной записи БД. Заполняются вручную только до первого запуска, после чего автоматически шифруются и очищаются. |
| `sdbuser` / `sdbpass` | Учётные данные, зашифрованные мастер-ключом (Base64). Заполняются автоматически. |

Строка подключения формируется только через `NpgsqlConnectionStringBuilder` — значения присваиваются по отдельности, конкатенация строк не применяется (инъекция в строку подключения исключена).

## Инициализация при старте

Инициализация выполняется в `Data.ReadConfigAsync` → `DatabaseSection.TryInitDatabaseAsync` (инициализатор секции вынесен из Data шагом 6 декомпозиции; возвращает готовый экземпляр `Database` либо null):

1) читаются и проверяются `dbhost`, `dbport`, `dbname`, `dbsslmode`;
2) берутся учётные данные из `sdbuser`/`sdbpass`; если их нет (первый запуск) — из `dbuser`/`dbpass`, значения шифруются мастер-ключом, записываются в `sdbuser`/`sdbpass`, открытые поля очищаются;
3) создаётся экземпляр `Database` (расшифровка учётных данных выполняется однократно — в его конструкторе);
4) выполняется проверка доступности `SELECT 1` через `Database.ValidateConnectionAsync`.

Проверка доступности БД выполняется асинхронно: `ReadConfigAsync` вызывается из `Program.Main` через `await` — синхронные обёртки над async (sync-over-async) не применяются.

Любая ошибка инициализации БД (недоступный сервер, невалидная сервисная запись, недоступный мастер-ключ) останавливает приложение (fail-fast) — так же, как и для домена AD (см. [[Пользователи]]).

## Сервисная инфраструктура схемы БД (каркас, дамп, сброс / обновление)

Реализовано по ТЗ «Сервисная инфраструктура БД» (дата 2026-11-05). Управляет жизненным циклом схемы `webshelf`: эталон структуры (файл-каркас), проверка при старте, дамп перед изменениями, полный сброс и обновление структуры, retention дампов.

### Порядок на старте (расширение существующего)

```
ReadConfigAsync
  → DatabaseSection.TryInitDatabaseAsync (создание Database + ValidateConnection)
  → DbBootstrapper.EnsureSchemaAsync (новый шаг, Program.Main после ReadConfigAsync)
       ├─ загрузка каркаса + манифест (SchemaSkeletonLoader/SchemaSkeletonParser)
       ├─ advisory lock PostgreSQL (сериализация конкурирующих экземпляров, дополнение к InstanceLock)
       ├─ чтение живой схемы (LiveSchemaReader) и сравнение (SchemaComparer)
       ├─ при расхождении:
       │    ├─ гейт dbautoschemareset (false → Error + приложение не стартует, данные не затрагиваются)
       │    ├─ дамп непустой схемы (DbDumper; ошибка дампа → изменения запрещены, fail-fast)
       │    └─ обновление структуры к каркасу (Structure Update; пустая схема — применение каркаса)
       └─ retention cleanup (DumpRetentionPolicy)
```

Вызов синхронен с точки зрения старта (`await`): приложение не начинает работу на «чужой» схеме.

### Файл-каркас

- `db/webshelf_skeleton.sql` (поставляется вместе с приложением, `CopyToOutputDirectory`), чистый SQL DDL без данных. Хеш содержимого (SHA-256) пишется в лог и в метаданные дампов.
- Манифест строится лёгким парсером из того же файла — расхождение «манифест vs SQL» исключено по построению (риск R8 ТЗ).
- Поддерживаемое подмножество: `CREATE SCHEMA`, `CREATE TABLE` (столбцы + PK/FK/UNIQUE/CHECK, включая inline в столбцах), `ALTER TABLE … ADD CONSTRAINT`, `ALTER TABLE … ADD [COLUMN]`, `CREATE SEQUENCE`, `CREATE [UNIQUE] INDEX`. Всё остальное (в т.ч. `serial`, `GENERATED … AS IDENTITY`, представления, функции) отклоняется при разборе — старт прерывается.
- Требование к явным последовательностям вместо serial: `CREATE SEQUENCE webshelf.t_id_seq …` + `DEFAULT nextval('webshelf.t_id_seq'::regclass)`.

### Определение «структура совпадает»

- Таблицы и столбцы: имя, тип (с нормализацией синонимов: int4/int → integer, varchar → character varying и т.п.), nullability, DEFAULT (нормализация: `nextval` без схемы/кавычек, приведение `::type` отбрасывается, `CURRENT_TIMESTAMP` ≡ `now()`, `NULL` ≡ отсутствие).
- Ограничения — по паре (вид, нормализованное определение), а не по имени; лишние скобки от `pg_get_constraintdef` и квалификация схемой игнорируются.
- Последовательности — по наличию (имени); индексы — имя, таблица, уникальность, выражение столбцов.
- Объекты вне поддерживаемого набора (представления, функции, триггеры, identity-столбцы, enum/domain) — расхождение; дамп такой схемы не создаётся (защита от неполного дампа, R3).

### Два режима приведения к каркасу

| Режим | Поведение |
| --- | --- |
| **Full Reset** | `DROP SCHEMA webshelf CASCADE` → `CREATE SCHEMA` → DDL каркаса. Все данные удаляются. Путь пустой схемы и явного программного вызова `DbBootstrapper.ResetToSkeletonAsync`. |
| **Structure Update** | Добавление недостающих таблиц/столбцов/ограничений/индексов/последовательностей; каскадное удаление объектов, отсутствующих в каркасе; выравнивание nullability/DEFAULT. **Типы существующих столбцов не меняются автоматически** (ALTER TYPE может молча преобразовать данные); остаточные расхождения типов допускаются контрольной проверкой. Режим автоматики старта (`EnsureSchemaAsync`) и программного вызова `UpdateStructureAsync`. |

Оба режима выполняются в одной транзакции с `SET LOCAL search_path`; каждая DROP-операция журналируется отдельным предупреждением (R13).

### Дамп (структура + данные)

- Только Npgsql — без `pg_dump`/`psql` на хосте. Формат — текстовый SQL: последовательности → таблицы (без FK) → данные `COPY … FROM STDIN` (текстовый формат PostgreSQL, поточная передача) → владение последовательностями → внешние ключи → индексы. Согласованный снимок: транзакция REPEATABLE READ.
- Имя файла: `webshelf_dump_ГГГГММДД_ЧЧММСС_ммм.sql` (UTC). Метаданные в заголовке: версия формата, время, версия приложения, хеш каркаса, БД/хост/порт/схема.
- Атомарность: запись во временный файл `*.tmp`, затем `File.Move`; при любой ошибке временный файл удаляется, изменения структуры не выполняются, приложение не стартует (fail-fast, R2).
- Каталог дампов не должен находиться внутри `wwwroot` (R14) — проверяется при чтении конфигурации.
- Восстановление — вручную (psql или как скрипт). Круговой обход (dump → restore) покрыт интеграционным тестом.

### Retention дампов

- Удаляются дампы старше `dbdumpretentiondays` (по умолчанию 90); дата берётся из имени файла (UTC), не из времени записи.
- Файл с максимальной меткой времени (последний дамп) не удаляется никогда (R11). Незавершённые `*.tmp` старше срока удаляются.
- Очистка выполняется при старте после основного потока bootstrap (в том числе на пути «схема совпадает»).

### Конфигурация (Server.conf)

| Ключ | Назначение | По умолчанию |
| --- | --- | --- |
| `dbschema` | Имя схемы (строчные латинские буквы, цифры, `_`) | `webshelf` |
| `dbskeletonpath` | Путь к SQL-каркасу (относительно каталога приложения или абсолютный) | `db/webshelf_skeleton.sql` |
| `dbdumpspath` | Каталог дампов (не внутри wwwroot) | `Data/DbDumps` |
| `dbdumpretentiondays` | Срок хранения дампов, дней (1–3650) | `90` |
| `dbautoschemareset` | Автоматическое приведение структуры к каркасу при несовпадении на старте | `false` (безопасный default) |

`dbautoschemareset=false` — единственная точка потенциально деструктивной автоматики заблокирована: расхождение схемы блокирует запуск (fail-fast), данные не затрагиваются (R1). Только явное `true` включает автоматику; перед любым изменением непустой схемы создаётся обязательный дамп.

### Требования к сервисной учётной записи PostgreSQL

Сервисная УЗ обязана уметь создавать и удалять схему `webshelf` и объекты в ней (owner схемы или эквивалентные права в рамках БД: `CREATE` по базе данных для `CREATE/DROP SCHEMA`). При нехватке прав — понятный Error и остановка приложения (R4).

### Логирование

Все сообщения — по правилам [[Логирование]]: перед деструктивным действием — `Warning` с полным контекстом (Host, Port, Database, Schema, причина, путь дампа, `dbautoschemareset`); успешный дамп — `Information`; успешный сброс/обновление — `Warning`; ошибка дампа — `Error` + исключение; пустая схема — `Information` («дамп пропущен»).

### Ручной сброс из UI

На данном этапе не реализуется. Метка для будущей реализации — в `DbBootstrapper` (TODO): страница Администратора «Сброс БД к каркасу» / «Обновление структуры БД» с двойным подтверждением, отображением последнего дампа, обязательным дампом перед действием и аудитом. Точка подключения — программные методы `ResetToSkeletonAsync` / `UpdateStructureAsync`.

### Классы (пространство `WebShelf.Classes.DB`)

- `SchemaManifest` и связанные записи — ожидаемая структура из каркаса.
- `SchemaSkeletonLoader` / `SchemaSkeletonParser` — загрузка и разбор каркаса (хеш SHA-256 + манифест).
- `LiveSchemaReader` — чтение живой схемы из каталогов PostgreSQL (параметризованные запросы).
- `SchemaComparer` / `SchemaDiff` — сравнение и полный перечень расхождений.
- `DbDumper` — дамп структуры и данных (Npgsql, текстовый SQL, COPY).
- `DbSkeletonApplier` — применение каркаса (Full Reset / Structure Update).
- `DumpRetentionPolicy` / `DbDumpFile` — имена и очистка дампов.
- `SchemaBootstrapperOptions` — параметры из Server.conf.
- `DbBootstrapper` — оркестратор (проверка → дамп → приведение → контрольная проверка → retention); advisory lock `pg_advisory_lock` на время bootstrap (R5).

## Хранение учётных данных

- Учётные данные сервисной записи БД хранятся **только в зашифрованном виде** (`sdbuser`/`sdbpass`). Шифрование — `CryptoEngine` (AES-256-CBC + HMAC-SHA256, Encrypt-then-MAC; инстансный singleton, поступает в `Database` конструктором — см. [[Инстансное шифрование]]), мастер-ключ — в реестре `HKCU\Software\WebShelf\Encryption` под защитой DPAPI текущей учётной записи (см. [[Пользователи]]).
- Первый запуск (шифрование `dbuser`/`dbpass`) и дальнейшая работа службы должны выполняться под одной и той же выделенной учётной записью (например, `DOMAIN\svc_webshelf`) — иначе DPAPI не сможет расшифровать мастер-ключ.
- **Решение (коммит 38):** при загрузке валидных `sdbuser`/`sdbpass` остаточные открытые `dbuser`/`dbpass` очищаются автоматически. Ранее они оставались в файле в открытом виде, хотя приложением уже не использовались.
- **Решение (коммит 38):** запись `sdbuser`/`sdbpass` (и `sdomainuser`/`sdomainpass`) в Server.conf выполняется атомарно — временный файл + `File.Replace`. Появление усечённого конфига при сбое питания или аварийном завершении процесса исключено.
- **Решение (коммит 38):** устранена двойная расшифровка учётных данных: `Data` больше не расшифровывает `sdbuser`/`sdbpass` для промежуточной проверки — расшифровка и валидация выполняются однократно в конструкторе `Database`.

## SSL/TLS

- По умолчанию `Require`: канал шифруется, сертификат сервера не проверяется. `VerifyCA`/`VerifyFull` — для проверки сертификата сервера, `Allow`/`Prefer` — компромиссные режимы без гарантии шифрования.
- **Решение (коммит 38):** `Allow` включён в перечень допустимых значений в шаблоне конфигурации и в сообщении об ошибке (валидный режим Npgsql, ранее в документации не упоминался, хотя принимался кодом).
- **Решение (коммит 38):** при `dbsslmode=Disable` в лог пишется `Warning` — пароль сервисной записи передаётся по сети в открытом виде. Предупреждение симметрично предупреждению о схеме `http` в `Program.cs`. Режим `Disable` допустим только внутри изолированного сегмента сети.

## Правила работы с соединениями и запросами

1) Соединения открываются только через `Data.Database.OpenConnectionAsync(cancellationToken)` — из пула `NpgsqlDataSource`. Соединение обязано освобождаться вызывающим кодом (`await using`) — контракт задокументирован на методе.
2) `CancellationToken` пробрасывается во все асинхронные вызовы БД.
3) SQL-запросы — только с параметрами (`@parameter` через Dapper-анонимные объекты или `NpgsqlCommand.Parameters`). Конкатенация и интерполяция строк в тексте запроса запрещены.
4) Таймаут установления соединения — 15 с (`Timeout`, совпадает с умолчанием Npgsql). Таймаут команды — умолчание Npgsql (30 с); при необходимости переопределяется на конкретной команде, глобально не меняется.
5) Повторное использование одного соединения разными операциями не допускается: каждая операция открывает соединение из пула и возвращает его. Исключение — bootstrap схемы (`DbBootstrapper`): весь его поток (advisory lock, чтение каталогов, применение каркаса) выполняется на одном соединении, так как advisory lock привязан к сессии; это одна логическая операция.
6) Логирование — по правилам [[Логирование]]: `Host`, `Port`, `Database`, `SslMode` писать можно; реальные учётные данные, пароли и строка подключения в логи не попадают; сервисная запись маскируется как `SystemAccount`. Комментирование — по правилам [[Комментирование]], типизация — по правилам [[Важные требования к коду]].

## Ограничения и дальнейшие шаги

- Схема БД управляется файлом-каркасом `db/webshelf_skeleton.sql` (см. раздел «Сервисная инфраструктура схемы БД»); первые таблицы добавляются в каркас по мере появления сущностей.
- Поддерживаемый набор объектов схемы: таблицы, столбцы, PK/FK/UNIQUE/CHECK, sequences, отдельные индексы. Функции, триггеры, представления, identity-столбцы и материализованные представления — вне объёма v1: их наличие в схеме блокирует дамп и изменения (fail-fast с понятной диагностикой).
- Structure Update не меняет типы существующих столбцов автоматически (защита от молчаливого преобразования данных); такие расхождения журналируются Warning и требуют ручной миграции.
- `Database` доступен через свойство `Data.Database` (экземпляр `Data` — единственный на процесс: создаётся при старте до сборки хоста и регистрируется в DI как singleton); прямая регистрация `Database` в DI и получение через внедрение зависимостей — направление на будущее, упрощающее unit-тестирование.
- Параметры пула соединений (`Max Pool Size`, время жизни простаивающих соединений и др.) пока остаются со значениями по умолчанию Npgsql; при росте нагрузки пересмотреть.
- Правила обработки ошибок PostgreSQL (`PostgresException`) и повторы идемпотентных операций определяются вместе с первыми таблицами; сервисная инфраструктура схемы фиксирует свои правила (дамп обязателен, транзакционность, fail-fast) в этом разделе.
