# Пользователи

## Системная учетная запись

Системная учетная запись, используемая для работы WebShelf с AD, должна быть создана до первого запуска приложения, защищена надежным паролем и иметь права на чтение AD (чтобы приложение могло находить пользователей и проверять членство в группах; права на редактирование AD понадобятся с появлением администрирования пользователей из самого WebShelf).

До первого запуска учетные данные нужно прописать в соответствующие поля конфигурационного файла в явном виде (`domainuser` / `domainpass`). После запуска, в целях безопасности, программа в автоматическом режиме шифрует эти данные мастер-ключом, сохраняет их в поля `sdomainuser` / `sdomainpass` и очищает открытые значения (реализовано, см. `Data.TryInitDomain`). Мастер-ключ хранится в реестре (`HKCU\Software\WebShelf\Encryption`) под защитой DPAPI текущей учетной записи, поэтому первый запуск и дальнейшая работа службы должны выполняться под одной и той же выделенной учетной записью (например, `DOMAIN\svc_webshelf`).

## Доступ к системе

Доступ к системе осуществляется через проверку учетной записи в AD. Проверка пользователя (реализовано, см. `Domain.ValidateAdCredentials`) осуществляется по следующим критериям:
1) Пользователь зарегистрирован в AD, пара Login / Password валидна (проверка выполняется от имени самого пользователя с подписыванием и шифрованием LDAP-канала - Negotiate + Signing + Sealing).
2) Учетная запись не отключена в AD.
3) Пользователь состоит в группе доступа `WebShelf-{InstanceIdShort}-Users`. (Данная проверка предназначена для предотвращения входа в систему пользователей, зарегистрированных в AD, но не имеющих отношения к WebShelf. Значение InstanceIdShort - первые 12 символов InstanceId (ULID) в нижнем регистре, печатается в лог при старте приложения. В Debug-сборке InstanceId фиксирован (26 нулей), поэтому при отладке на разных компьютерах все экземпляры ссылаются на одни и те же группы WebShelf-000000000000-*; см. [[Группы пользователей]].)

**Решение (коммит 32):** первоначальный вариант проверки - строка "*GUID|guid*" в поле "*info*" учетной записи - заменен на проверку членства в группе AD. Группы администрируются штатными средствами AD, не требуют кастомных атрибутов и ручного заполнения полей учетных записей. Требование к содержимому поля "*info*" более не применяется.

**Ограничение текущей реализации:** проверяется только прямое членство в группе (без вложенных групп). Это следует учитывать при проектировании ролевой модели: пользователи должны включаться в ролевые группы напрямую.

Защищенные страницы дополнительно закрыты атрибутом `[Authorize]`: неаутентифицированный запрос документа отклоняется на уровне endpoint (редирект на `/entry?ReturnUrl=...`) еще до построения circuit Blazor.

### Разделение учетных записей по уровню привилегий

**Реализовано.** Разделение учетных записей по уровню привилегий осуществляется путем добавления или удаления пользователя из заранее определенных групп AD (см. [[Группы пользователей]]).

0) Администратор - Максимальный уровень доступа. (В системе, в каждый момент времени, должен быть минимум один администратор)
1) Директор - Права менеджера + возможность менять роли и разделы всех пользователей системы.
2) BIM-менеджер - Права менеджера + специальные функции доступные только BIM-менеджеру.
3) Менеджер - Разрешен доступ к документации, всех объектов. (При создании объекта должен указать ГИП-а ответственного за проект. Может сам выбирать и создавать объекты, а также назначать на них исполнителей из любого раздела)
4) ГИП - Разрешен доступ к документации, всех объектов. (Может сам выбирать и создавать объекты, а также назначать на них исполнителей из любого раздела)
5) Руководитель группы - Разрешен доступ к документации, заранее определенных разделов, всех объектов. (Может сам выбирать объекты и назначать на них исполнителей из своего раздела)
6) Исполнитель - Разрешен доступ к документации, заранее определенных разделов, всех объектов. (Может сам выбирать объекты)
7) Внешний исполнитель - Разрешен доступ к документации, заранее определенных разделов, назначенных объектов. (Не может сам выбирать объекты)
8) Заказчик - Разрешен просмотр и выгрузка выданной документации по выбранным объектам.
9) Гость - Неменьшее количество привилегий, запрещено любое редактирование. Разрешен просмотр только выбранных элементов.

### Вычисление роли (реализовано)

Эффективная роль вычисляется по прямым группам AD: при членстве в нескольких ролевых группах действует старшая роль (наименьший индекс старшинства — задается в `AppRoleCatalog`); пользователь без единой ролевой группы получает роль «Гость». Под Гостя группа в AD не создается: это fallback при отсутствии совпадений.

Мгновенная смена роли обеспечивается сочетанием трех механизмов (варианты 1+2+3):

1) **TTL-кэш роли** в резолвере (`RoleResolver`, ключ `rolettl` в `Server.conf`, по умолчанию 60 с, диапазон 10–300 с): в пределах TTL роль берется из кэша без обращения к AD.
2) **Фоновый опрос** ролевых групп с заданным интервалом (ключ `rolepoll`, по умолчанию 30 с): смена роли в AD доезжает до открытых circuit'ов не позже этого интервала — служба `RoleRefreshService` рассылает событие через `RoleChangeNotifier`, провайдер состояния аутентификации обновляет клейм роли и уведомляет Blazor; лента и `AuthorizeView` перерисовываются без перезагрузки страницы.
3) **Свежая LDAP-проверка в обход кэша** при входе и перед критичными операциями (`RoleResolver.ResolveFresh`).

Принципы безопасности:

- Cookie хранит только личность; клейм роли в cookie — транспорт на момент входа, источник истины всегда AD.
- При недоступности AD действует последнее известное значение роли (stale-if-error); при отсутствии кэша вход отклоняется (fail-secure).
- Исключение из группы Users — принудительный выход: активные circuit'ы переводятся в анонимное состояние (принудительный sign-out), пользователь отправляется на форму входа.
- Смена роли и принудительный выход фиксируются в лог (аудит).

Текущая роль отображается в UI на ленте между логином и кнопкой «Выход» в квадратных скобках: `ivanov [Администратор] Выйти`.
