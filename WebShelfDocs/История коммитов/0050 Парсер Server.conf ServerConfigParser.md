# 0050 — Парсер Server.conf ServerConfigParser

## Суть изменений

- Шаг 5 дорожной карты декомпозиции: из `Data` в новый класс `Classes/Service/Configuration/ServerConfigParser.cs` вынесен парсер `ReadConfigFile` — чтение файла Server.conf в словарь ключ=значение (ключи без учёта регистра, OrdinalIgnoreCase; комментарии `#` и пустые строки пропускаются; при дубликатах побеждает последнее значение).
- Класс инстансный, путь к файлу внедряется конструктором (предпочтение дорожной карты после улучшения У2 шага 0 — как путь `Data`): `Data` создаёт парсер один раз в конструкторе на своё свойство `ConfigFile` и передаёт его в readonly-свойство `ConfigParser`. Производственных точек вызова парсера одна — `ReadConfigAsync`.
- Перенос механический: тело метода перенесено дословно (проверено автосравнением с HEAD с точностью до пробелов, 49 строк). Правки переноса: константа `Class=` в логах перенесённого кода (`WebShelf.Classes.Service.Data` → `WebShelf.Classes.Service.Configuration.ServerConfigParser`, принцип 6 дорожной карты) и перенос пути из параметра метода в конструктор (значение в производстве то же — путь `ConfigFile`).
- `Data` остаётся оркестратором чтения (единая зона «хранение и инициализация конфигурации»): получает словарь у парсера, выполняет последовательность `TryInit*`, сбрасывает состояние при отказе — порядок сброса не менялся. Сообщения логов сохранены дословно (кроме `Class=`); признак ошибки парсера — пустой словарь с сообщением «Файл конфигурации пуст или не содержит валидных записей» — остался в оркестраторе. Кодировка UTF-8 (с BOM и без), поведение при дубликатах — под защитой characterization-тестов шага 0.
- Парсер не объединялся с записью конфигурации (запись — отдельный шаг 6: у чтения и управляемой перезаписи разные ответственности).
- Тесты: 14 методов (15 кейсов) шага 0 переписаны с вызова `Data.ReadConfigFile` на прямой вызов `ServerConfigParser` — изменена только обёртка `ParseFile` (тела и ожидания не менялись, автосравнение 14/14); тесты оркестрации `ReadConfigAsync` остались против `Data`. Файл тестов сохраняет имя `DataConfigParserTests.cs`: протокол передачи патча — полные копии файлов заменой, удаления файлов патчем не выражаются; класс по-прежнему покрывает парсинг конфигурации Data. Добавлено 3 прямых теста нового API: файл без валидных записей → пустой словарь без исключения (парсерная половина признака ошибки); переводы строк CRLF (файлы редакторов Windows) разбираются как LF; конструктор с `null`-путём → `ArgumentNullException`.
- Осознанные решения: 1) конструктор парсера отвергает `null` fail-fast (`ArgumentNullException.ThrowIfNull`) — новая публичная граница класса, тест новой точки ветвления требуется §5 дорожной карты; 2) парсер создаётся в конструкторе `Data` один раз и не логирует при создании — состав стартовых сообщений лога не изменился; 3) `using WebShelf.Classes.Service.Configuration` в `Data.cs` — единственная механическая правка usings.
- Метрики: `Data.cs` 1219 → 1165 строк; `ServerConfigParser.cs` — 129 строк; атрибутов `[Fact]`/`[Theory]` 235 → 238; тест-кейсов 347 → 350. Критерий шага «`Data` ≤ ~1070» выведен из размера на момент составления плана (1140 строк); шаг 0 увеличил `Data` на 78 строк (У2 и XML тестовых точек), сопоставимая цель — ~1148; фактический результат 1165, превышение — XML-документация новой точки внедрения парсера и актуализация remarks (по прецеденту шага 3: 672 при цели «~650»).
- Попутно закрыты остаточные действия шага 4 (по прецеденту дозаполнения хешей 0045–0047 коммитом шага 3 и 0048 — коммитом шага 4): на страницу 0049 вписан хеш коммита шага 4 (`b292cf6`); страница 0021 «Шифрование и мастер-ключ» дополнена ссылкой о новом расположении кода мастер-ключа (`Classes/Crypto/KeyStore.cs`, замечание из отметки шага 3, в патч шага 4 не входившее).
