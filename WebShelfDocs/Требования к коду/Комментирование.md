## Комментирование кода в WebShelf

### Назначение

Комментарии в проекте служат для быстрого понимания назначения типов, методов и неочевидных участков логики. Язык комментариев — **русский**. Стиль документации C# — **XML-комментарии** (`///`), для JavaScript — **JSDoc**.

### Общие правила

1. **Подробно комментируются** классы, записи (record), свойства, методы и параметры.
2. **Специфичные и труднопонимаемые** фрагменты внутри методов поясняются обычными комментариями `//` на русском.
3. Комментарии описывают **смысл и поведение**, а не дословно повторяют код.
4. Имена типов, членов и параметров в тексте ссылок оформляются через XML-теги (`<see cref="..."/>`, `<c>...</c>`, `<see langword="null"/>` и т.п.).
5. Не оставлять устаревшие или вводящие в заблуждение комментарии при изменении кода.

### C# / Blazor: XML-документация

#### Классы и record

Перед объявлением типа — блок `<summary>` с кратким описанием роли в системе.

```csharp
/// <summary>
/// Представляет домен Active Directory и предоставляет методы
/// для получения пользователей системы и проверки учётных данных.
/// </summary>
internal class Domain
```

Для record с позиционными параметрами — `<summary>` у типа и `<param>` у каждого параметра:

```csharp
/// <summary>
/// Краткая информация о пользователе Active Directory,
/// необходимая для отображения в WebShelf.
/// </summary>
/// <param name="SamAccountName">Логин (sAMAccountName).</param>
/// <param name="DisplayName">Отображаемое имя.</param>
/// <param name="Email">Адрес электронной почты (атрибут mail).</param>
internal sealed record AdUserInfo(string SamAccountName, string DisplayName, string Email);
```

#### Свойства и поля

У публичных и внутренних свойств — `<summary>`. При необходимости указывается допустимое «пустое» состояние:

```csharp
/// <summary>
/// Схема прослушивания: <c>http</c> или <c>https</c>.
/// <see langword="null"/>, если не задана или некорректна.
/// </summary>
internal static string? Scheme { get; private set; }
```

#### Методы

Минимальный набор для значимых методов:

| Тег           | Когда использовать                                     |
| ------------- | ------------------------------------------------------ |
| `<summary>`   | Всегда — что делает метод                              |
| `<param>`     | Каждый параметр                                        |
| `<returns>`   | Если метод что-то возвращает                           |
| `<exception>` | Если метод явно выбрасывает исключения                 |
| `<remarks>`   | Сложные правила, форматы входа, ограничения            |
| `<example>`   | Неочевидное API (нормализация имён, фильтры AD и т.п.) |

Пример:

```csharp
/// <summary>
/// Читает файл Server.conf и инициализирует <see cref="Domain"/>, <see cref="GUID"/>,
/// <see cref="Port"/> и <see cref="Scheme"/>.
/// </summary>
/// <returns>
/// <see langword="true"/>, если конфигурация прочитана успешно;
/// <see langword="false"/> — при любой ошибке.
/// </returns>
internal static bool ReadConfig()
```

Конструкторы документируются так же, с `<param>` и при необходимости `<exception cref="ArgumentException">`.

#### Методы в Razor-компонентах

В блоке `@code` у параметров `[Parameter]` и у методов жизненного цикла / обработчиков — те же XML-комментарии:

```csharp
/// <summary>
/// Заголовок окна, отображаемый в title-bar.
/// </summary>
[Parameter]
public string Title { get; set; } = "WebShelf";

/// <summary>
/// Инициализация: чтение ошибки из query-string и проверка аутентификации.
/// </summary>
protected override async Task OnInitializedAsync()
```

В разметке допустимы краткие пояснения в `@* ... *@` (назначение блока UI, связь со стилями/скриптами).

#### Локальные методы и endpoint’ы в Program.cs

Обработчики minimal API и вспомогательные функции сопровождаются `<summary>`:

```csharp
/// <summary>
/// Обработчик POST /account/login — проверка учётных данных AD и выдача cookie.
/// </summary>
static async Task<IResult> LoginAsync(HttpContext context, IConfiguration config)
```

### Внутриметодные комментарии

Используются для:

- неочевидных условий и фильтров (LDAP, битовые флаги AD);
- важных ограничений безопасности (например, что `DirectoryEntry` не освобождается отдельно);
- шагов многоэтапной логики (нормализация UPN / `DOMAIN\user`).

```csharp
// Фильтр: пользователь, включённая учётная запись, нужный GUID в поле info
// DirectoryEntry принадлежит UserPrincipal — отдельно не освобождаем
```

Не комментировать каждую тривиальную строку (`i++`, присваивание без логики).

### JavaScript

Файлы и публичные функции — JSDoc на русском (допустимо краткое описание API на русском + типы параметров):

```javascript
/**
 * window.js — общая логика окон WebShelf.
 * Перетаскивание, кнопка закрытия, переключатель видимости пароля.
 *
 * API (вызывается из Blazor через JS interop):
 *   WebShelfWindow.init(elementId, options)
 *   WebShelfWindow.dispose(elementId)
 */

/**
 * Инициализирует поведение окна по id корневого элемента.
 * @param {string} elementId - id элемента .ws-window
 * @param {{ canClose?: boolean, closeBubbleText?: string, center?: boolean }} options
 */
function init(elementId, options) { ... }
```

Секции внутри функции можно помечать короткими заголовками (`// --- Перетаскивание ---`).

### Чего избегать

- Комментариев только на английском в прикладном коде (кроме устоявшихся технических имён: LDAP, GUID, UPN).
- Пустых `<summary>` без смысла.
- Дублирования имени метода в summary без добавления смысла («Метод ReadConfig читает конфиг» → лучше описать *что инициализируется и при каком результате true/false*).
- Закомментированного мёртвого кода без пометки, зачем он сохранён.

### Связь с другими требованиями

Комментирование **не заменяет** логирование: в catch-блоках по-прежнему пишется класс и метод через Serilog / `ILogger<T>` (см. [[Логирование]]).
