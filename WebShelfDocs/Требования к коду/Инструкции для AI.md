
## Обязательные правила:

1. Сначала проверять целевую платформу и доступную версию языка.
2. Использовать возможности C# 14, если проект ориентирован на `.NET 10`.
3. Использовать более новые возможности только при подтверждённой поддержке целевой платформой.
4. Не генерировать код в стиле старых версий C#, если современная конструкция делает его проще.
5. Во всех примерах и генерируемых фрагментах использовать явную типизацию.
6. Не использовать `var`, даже если компилятор способен вывести тип.
7. Предпочитать collection expressions для поддерживаемых типов.
8. Предпочитать primary constructors для простых случаев передачи зависимостей.
9. Использовать raw string literals для многострочных текстов.
10. Использовать records для подходящих моделей данных.
11. Обязательно учитывать nullable reference types.
12. Предпочитать асинхронные API для операций ввода-вывода.
13. Поддерживать передачу `CancellationToken`.
14. Не создавать лишние абстракции и шаблонный код.
15. Не жертвовать читаемостью ради минимального количества строк.
16. Не использовать устаревшие API, если имеется современная поддерживаемая альтернатива.
17. Не придумывать API, методы или свойства, которых нет в целевой версии .NET.
18. Учитывать ограничения конкретных библиотек и NuGet-пакетов.
19. Не менять архитектуру проекта без необходимости.
20. При рефакторинге сохранять функциональное поведение, контракты и совместимость.

## Требования по оптимизации структуры проекта

1. Писать код сразу в декомпозированном виде: с чётким разделением ответственности, минимальной связанностью между модулями и возможностью расширения без необходимости последующего разбиения существующих сущностей.
2. Расширять существующие классы допускается только в том случае, если добавляемый код относится к той же зоне ответственности, что и сам класс. Если новая логика выходит за рамки текущей ответственности класса — её необходимо выносить в отдельный модуль/класс.
## Проверка качества перед выдачей кода

Перед предоставлением результата необходимо проверить:

- соответствие целевой версии C#;
- совместимость API с .NET 10;
- отсутствие `var`;
- отсутствие необоснованных устаревших конструкций;
- корректность nullable-аннотаций;
- корректность асинхронного кода;
- отсутствие неиспользуемых переменных и импортов;
- корректность обработки исключений;
- соответствие существующей архитектуре;
- возможность компиляции кода.

## Критерий принятия решения

При выборе между двумя вариантами реализации руководствоваться следующим приоритетом:

1. Корректность и безопасность.
2. Совместимость с целевой платформой.
3. Читаемость и простота сопровождения.
4. Простота и выразительность.
5. Производительность.
6. Минимизация шаблонного кода.

При этом производительность становится приоритетным критерием в тех случаях, когда она является явно заданным требованием.
