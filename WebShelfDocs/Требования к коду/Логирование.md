## Назначение

Все значимые события и исключения пишутся в единый журнал через **Serilog**, чтобы по записи можно было однозначно определить **класс** и **метод**, где произошло событие.

## Инфраструктура

- Ранний bootstrap-логгер (`Log.Logger`) — до построения хоста (в т.ч. ошибки чтения `Server.conf`).
- После `WebApplication.CreateBuilder` — `builder.Host.UseSerilog(...)`.
- После `Build` — `app.UseSerilogRequestLogging()` для HTTP-запросов.
- В конце работы приложения — `Log.CloseAndFlush()`.
- Файлы: `logs/webshelf-.log`, ротация по дням, хранение 30 файлов.
- Уровни: по умолчанию Information; `Microsoft.AspNetCore` и `Microsoft.AspNetCore.Components` — Warning.

## Обязательные правила

1. **Методы оборачиваются в try-catch.**  
   При исключении запись идёт в логгер (не в `Console`).

2. **В каждой записи указываются класс и метод** через именованные свойства:
   - `Class={Class}` — полный идентификатор типа (например, `WebShelf.Classes.DC.Domain`);
   - `Method={Method}` — имя метода (`nameof(...)` или `"Main"` / `".ctor"`).

3. **Исключения** логируются с передачей объекта исключения первым аргументом:

```csharp
Log.Error(ex, "… Class={Class}, Method={Method}, …", ClassName, method, …);
// или в компонентах:
Logger.LogError(ex, "Исключение в {Class}.{Method}", ClassName, nameof(MethodName));
```

4. **Источник логгера:**
   - статические классы и `Program` — статический `Serilog.Log`;
   - Blazor-компоненты и сервисы с DI — `ILogger<T>` (`@inject ILogger<T> Logger`).

5. **Константа имени класса** в типе:

```csharp
private const string ClassName = "WebShelf.Classes.Service.Data";
```

В начале метода:

```csharp
const string method = nameof(ReadConfig);
```

6. **Не использовать** `Console.Write` / `Console.Error` для прикладных ошибок и исключений.

## Рекомендуемые уровни

| Уровень | Когда |
|--------|--------|
| **Fatal** | Приложение не может стартовать (конфиг, критический сбой в `Main`) |
| **Error** | Исключения, сбои AD/конфигурации, ошибки, после которых операция не выполнена |
| **Warning** | Ожидаемые отказы (неверный пароль, пустые поля, пользователь без GUID) |
| **Information** | Старт/успех операций (конфиг загружен, список пользователей получен) |
| **Debug** | Детали отладки (создание Domain, пропуск записей без sAMAccountName) |

## Примеры форматов сообщений

**Исключение (единый краткий шаблон для UI/endpoint):**

```text
Исключение в {Class}.{Method}
```

**Ошибка с контекстом (доменный код):**

```text
Ошибка при проверке учётных данных. Class={Class}, Method={Method}, Domain={Domain}, Username={Username}
```

**Информационное событие:**

```text
Конфигурация успешно загружена. Domain={Domain}, … Class={Class}, Method={Method}
```

## Что не писать в лог

- Пароли и значения `domainpass`.
- Полные тела HTTP-запросов с секретами.
- Избыточный шум на Information в горячих циклах (при необходимости — Debug).

## Ожидаемое поведение Blazor

Исключения `JSDisconnectedException` и `InvalidOperationException` при prerender / разрыве цепи interop **не** считаются сбоями приложения: их можно игнорировать или логировать на Debug, без уровня Error.
